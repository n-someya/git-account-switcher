# git-accunt-switcher — Architecture Decision Records

各 ADR は Context / Decision / Consequences / Alternatives の形式で記述する。

## ADR-0001: 双方向同期ではなく、単一マニフェストからの生成器とする

**Status:** Accepted

### Context

解決すべき課題は「ディレクトリ → アカウントの対応ルールが `~/.gitconfig` と `.envrc` の2箇所に重複する」ことである。

素朴な解決案は「2ファイルを同期するツール」だが、これは以下を抱え込む。

- 双方向の差分検出が必要
- どちらが正か判定できない衝突ケースが生じる（両方が独立に編集された場合）
- 手編集を許すため、パーサではなく編集器を実装することになる
- 「薄いラッパー」で済まなくなり、保守対象が増える

### Decision

**宣言的マニフェスト（`accounts.toml`）を唯一の情報源とし、`~/.gitconfig` / `~/.ssh/config` / `.envrc` はすべて再生成可能な派生物として扱う。**生成は一方向のみ。生成物の手編集はサポートせず、検出して警告する。

### Consequences

- 重複が構造的に消える。ルールの追加・削除はマニフェスト1箇所の編集で完結する
- 実装が冪等な出力処理に還元される。衝突解決ロジックが不要になる
- 端末の再構築が `accounts.toml` を配置して `apply` するだけになる（副次的利益）
- 一方で、既存の手書き設定からの**移行**が必要になる。`init` に推測インポートを持たせて緩和する
- 生成物を手で直したいケース（一時的な例外）に応えられない。マニフェストに `extra_config` のようなエスケープハッチを設ける余地を残す

### Alternatives considered

| 案 | 却下理由 |
| --- | --- |
| 双方向同期 | 上記の複雑性。「薄いラッパー」という当初の設計意図に反する |
| `.gitconfig` を正とし `.envrc` を導出 | 方向は正しいが、`.gitconfig` は git のための表現であり、`login` や `ssh_host_alias` のような git が知らない情報を置く場所がない。専用マニフェストのほうが素直 |
| 生成せず、実行時に毎回解決 | git の `includeIf` は静的ファイルを要求するため、git 側は生成が避けられない |

## ADR-0002: 生成物はユーザー手書き設定と物理的に分離し、接続は1行の手動追加とする

**Status:** Accepted

### Context

`includeIf` は git が読むファイルに書かれている必要がある。素朴には `~/.gitconfig` にマーカーコメント付きの管理ブロックを書き込む方式（`# BEGIN gh-multiaccount` … `# END`）が考えられる。

しかし `~/.gitconfig` はユーザーが長年育てた設定であり、ツールが書き込む対象にするとバグ1つで失う。

実機検証（T1）で、**`[include]` されたファイル内の `includeIf` も評価される**ことを確認した。

```
~/.gitconfig
  └─ [include] path = ~/.config/gh-multiaccount/git/includes.gitconfig
                        └─ [includeIf "gitdir/i:~/Developer/X/"]
                             path = .../account-x.gitconfig   ← 評価される
```

### Decision

**生成物は `~/.config/gh-multiaccount/` 配下にのみ書き出す。ユーザーの `~/.gitconfig` と `~/.ssh/config` には一切書き込まない。**接続に必要な1行は標準出力に提示し、ユーザー自身に追加させる（初回のみ）。

- git: `[include] path = ~/.config/gh-multiaccount/git/includes.gitconfig`
- ssh: `Include ~/.config/gh-multiaccount/ssh/config`

### Consequences

- ユーザーの手書き設定を破壊する経路が存在しなくなる。NFR-2 の大部分がこの決定で満たされる
- アンインストールが「1行消して1ディレクトリ削除」で完結する
- 生成物の全体を `git diff` で確認できる（`~/.config/gh-multiaccount/` 自体をバージョン管理できる）
- 初回セットアップに手動ステップが1つ増える。`doctor` の D2 / D3 で未接続を検出して緩和する
- `ssh_config` は「最初に得られた値が使われる」仕様のため、`Include` の**位置**が意味を持つ。先頭付近に置く必要があることをドキュメントと `doctor` D3 で担保する

### Alternatives considered

- **`~/.gitconfig` へのマーカーブロック書き込み**: 手動ステップは消えるが、ユーザー資産への書き込み権を得る代償が大きい。却下
- **`~/.gitconfig` 自体を生成物にする**: ユーザーの既存設定をすべてマニフェストに取り込む必要があり、スコープが際限なく膨らむ。却下

## ADR-0003: `.envrc` にアカウント名を埋め込まず、解決を `gh-multiaccount env` に委譲する

**Status:** Accepted

### Context

実機検証で、**git と direnv の判定基準が異なる**ことが判明した。

- `git` の `includeIf "gitdir:"` は **gitdir（`.git` の実パス）**に対して評価される（T4）
- `direnv` は **cwd** に対して `.envrc` を探索する

この差は通常のリポジトリでは表面化しないが、**linked worktree で食い違う**（T6）。ルート外に `git worktree add` したディレクトリは、gitdir が元リポジトリの `.git/worktrees/` を指すため、git は元アカウントを適用する。一方 direnv は worktree の物理位置を見るため、別アカウント（あるいは未設定）を適用する。submodule も同様の構造を持つ。

素朴な実装（`.envrc` に `export GH_CONFIG_DIR=".../gh-x"` とハードコード）は、このケースで git と矛盾する。そして矛盾は静かに起きる。

### Decision

**生成する `.envrc` にアカウント固有の値を一切埋め込まない。**

```bash
# .envrc — generated by gh-multiaccount. DO NOT EDIT.
eval "$(gh-multiaccount env --shell bash)"
```

`gh-multiaccount env` は以下の順序でアカウントを解決する。

1. `git config --get ghmultiaccount.account` — リポジトリ内なら git 自身が答えを出す
2. マニフェストの `roots` に対する cwd 前方一致 — リポジトリ外（T7）のフォールバック

`ghmultiaccount.account` はアカウント別 git 設定ファイルに生成器が書き込む。したがって **`env` が呼ばれる限り、git の判定がそのまま gh の判定になる。**

### Consequences

`.envrc` にアカウント名を埋め込む素朴な実装との差を、検証したケースごとに整理する。

| ケース | 素朴な実装（cwd 判定） | 本決定（git 委譲） |
| --- | --- | --- |
| 通常のリポジトリ（ルート配下） | 一致 | 一致 |
| **X のリポジトリの worktree を Y のルート配下に置く** | **不一致**（git は X、cwd は Y） | **一致**（git に問うため X） |
| X のリポジトリの worktree を全ルート外に置く | 不一致 | **direnv 経路では未解決**（下記） |
| Y 由来の submodule を X のリポジトリに埋める | 不一致（git は親の X を適用） | 一致（git に問うため X） |

- クロスルートの worktree・submodule という、**実際に起こりうる不一致が解消される**（検証済み）
- ただし**全ルート外に置かれた worktree は direnv 経路では解決できない。**そこには `.envrc` が存在せず direnv が発火しないため、`env` 自体が呼ばれない。この場合 gh は active account にフォールバックする。`shell_integration = "wrapper"`（ADR-0006）はすべての `gh` 呼び出しで発火するため、このケースも解決する。`doctor` の D7 でルート外 worktree を列挙し、ルート内への移動か wrapper 方式かを案内する
- `.envrc` の内容が全ルートで同一になる。生成物としても、レビュー対象としても単純
- ルートを追加・削除しても、既存 `.envrc` の再生成が不要（内容が変わらない）
- `direnv allow` の再実行が不要（`.envrc` の内容が変わらないためハッシュが変わらない）。運用上の利点が大きい
- `gh-multiaccount` バイナリが PATH に必要になる。バイナリ不在時に `.envrc` が失敗するため、`command -v` でガードし、不在時は警告のみで通す実装にする
- `cd` ごとに `git config` の呼び出しが1回入る。実測で数 ms 程度であり許容する。必要なら結果をキャッシュする

### Alternatives considered

- **`.envrc` にアカウント名を埋め込む**: T6 で git と矛盾する。却下
- **`.envrc` で直接 `git config --get` を呼ぶ**（バイナリを介さない）: リポジトリ外のフォールバックが `.envrc` 内のシェル実装になり、マニフェストの解析をシェルで書くことになる。却下
- **`direnv` の `source_up` を使い、`~/Developer/.envrc` 1枚に集約**: ルールが `.envrc` に戻ってくるため重複が復活する。却下

## ADR-0004: gh への資格情報受け渡しは、direnv 経路では `GH_CONFIG_DIR`、ラッパー経路では `GH_TOKEN` とする

**Status:** Accepted

### Context

`gh` にアカウントを指定する経路は2つある。いずれも[公式に文書化された環境変数](https://cli.github.com/manual/gh_help_environment)である。

| 方式 | 仕組み | 特徴 |
| --- | --- | --- |
| `GH_CONFIG_DIR` | gh の設定ディレクトリごと分離。アカウントごとに `gh auth login` する | トークンは gh の store に留まり、環境変数に露出しない。拡張・エイリアスはアカウント間で共有されない |
| `GH_TOKEN` | `gh auth token --user {login}` でトークンを取得し環境変数で渡す。gh のネイティブ多アカウント機能（v2.40.0+）をそのまま使う | 設定ディレクトリが1つで済み拡張が共有される。ただしトークンが環境変数に載る |

ここで direnv とシェル関数ラッパーの性質差が効いてくる。

**direnv は環境変数をシェルに永続的にエクスポートする。**そのシェルから起動されるすべての子プロセス — `npm install` のライフサイクルスクリプト、任意のビルドツール、テストランナー — が環境変数を読める。`GH_TOKEN` をこの経路に置くと、トークンの露出面がシェルセッション全体に広がる。

**シェル関数ラッパーは1回の呼び出しにだけ変数を渡せる**（`GH_TOKEN="$tok" command gh "$@"`）。露出は gh プロセスのみ。

### Decision

- **direnv 経路（既定）: `GH_CONFIG_DIR` を使う。**トークンを環境変数に置かない
- **シェル関数ラッパー経路: `GH_TOKEN` を per-invocation で渡す。**設定ディレクトリを分離しない
- どちらの経路でも、`gh auth` サブコマンドは素通しする（`GH_TOKEN` 設定下では `login` / `logout` / `switch` / `status` が誤動作するため）
- `gh auth switch` は**使わない。**グローバル状態を書き換え、他のターミナルセッションに干渉する

### Consequences

- direnv 経路でトークンが環境変数に載らない。子プロセスからの意図しない読み取りがなくなる
- 代償として、direnv 経路では拡張・エイリアス・`gh config` がアカウント間で共有されない。`doctor` で拡張の差異を報告するか、`sync-extensions` 相当を将来検討する
- direnv 経路はアカウントごとに `gh auth login` が必要。`init` の案内に含める
- ラッパー経路は `gh auth token` の呼び出しが1回入る（数十 ms）。許容する
- グローバル状態を書き換えないため、複数ターミナルで異なるアカウントを同時に扱える

### Alternatives considered

- **どちらの経路でも `GH_TOKEN`**: 実装が単一化するが、direnv でのトークン露出を受け入れられない。却下
- **どちらの経路でも `GH_CONFIG_DIR`**: 一貫するが、ラッパー経路では露出リスクがないのに拡張共有を捨てることになる。却下
- **`gh auth switch` をラップ**: グローバル状態の書き換えにより並行セッションが壊れる。却下

## ADR-0005: 実装言語は Rust とする

**Status:** Accepted

### Context

候補は Rust / Go / TypeScript / シェルスクリプト。要件側の制約は NFR-4（単一バイナリ・実行時依存ゼロ）と NFR-5（実 git バイナリに対する統合テスト）。

`.envrc` から `cd` ごとに呼ばれるため起動時間も要件になる。

### Decision

**Rust を採用する。**

### Consequences

- 単一バイナリ・実行時依存ゼロ。NFR-4 を満たす
- 起動時間が短く、`cd` ごとの呼び出しに耐える
- 型システムがマニフェスト検証（ルート重複、`id` の形式）を表現しやすい。`serde` + `toml` でスキーマを型として書ける
- `insta` によるゴールデンテストが NFR-5 に合致する
- **懸念: TypeScript が普段のスタックであり、Rust の保守速度は落ちる。**ツールの性質（小さく、要件が安定し、変更頻度が低い）を踏まえれば許容できると判断する
- ビルド時間と CI 時間は増える。クロスコンパイルは `cargo-dist` 等で自動化する
- 秘密情報を扱う経路（ADR-0004 のラッパー方式）で、`Debug` 導出の制御や `zeroize` によるメモリ消去といった手当てが型レベルで書ける

### Alternatives considered

| 案 | 却下理由 |
| --- | --- |
| Go | 単一バイナリ・起動速度・gh 拡張との親和性で有力。Rust に対する優位は主にビルド時間と学習コスト。Q1（ツール名・gh 拡張として配布するか）が「拡張として配布する」に決まる場合は再検討の価値がある |
| TypeScript / Node.js | 開発速度は最速だが、Node ランタイム依存と `npm -g` 前提が NFR-4 に反する。`cd` ごとの起動コストも Node では無視できない |
| シェルスクリプト | インストールは最軽量だが、TOML の解析・パス正規化・冪等な生成をシェルで書くのは保守性が早期に破綻する。NFR-5 のテスト水準も達成しづらい |

---

## ADR-0006: direnv を必須依存とせず、シェル関数ラッパーを同梱する

**Status:** Accepted

### Context

`.envrc` 方式は direnv のインストールと `direnv allow` を前提とする。OSS として公開する場合、direnv を使わない利用者を排除したくない。

一方、direnv には `.envrc` の承認モデルという明確な利点がある（生成物が勝手に実行されない）。

### Decision

`shell_integration` をマニフェストで選択可能にする。

- `"direnv"`（既定）: 各ルートに `.envrc` を生成
- `"wrapper"`: `~/.config/gh-multiaccount/shell/wrapper.zsh` を生成。`gh` を関数でラップし、`GH_TOKEN` を per-invocation で渡す（ADR-0004）
- `"none"`: git / ssh の生成のみ。gh の切替は行わない

### Consequences

- direnv 未導入でも導入できる。OSS としての採用障壁が下がる
- 経路が2つになり、テストマトリクスとドキュメントが増える
- `"wrapper"` はシェル関数のため、非インタラクティブシェル・IDE から直接呼ばれる `gh`・CI では効かない。`"direnv"` も cwd ベースであり同様の限界がある。**この限界は本ツールでは解消できず、#12459 の実装を待つ必要がある**ことを README に明記する

### Alternatives considered

- **direnv 必須**: 実装とドキュメントは単純になるが、採用障壁を上げる。却下
- **ラッパーのみ**: direnv 利用者（本プロジェクトの発端）の既存ワークフローを壊す。却下

## ADR-0007: SSH 鍵の生成と GitHub への登録はスコープ外とする

**Status:** Accepted

### Context

初期セットアップの体験を考えると、`ssh-keygen` と公開鍵の GitHub 登録まで面倒を見たくなる。`gh ssh-key add` があるため技術的には可能である。

### Decision

**鍵の生成・登録は行わない。**マニフェストで宣言された鍵の存在とパーミッションを `doctor`（D4）で検査し、不足時は実行すべきコマンドを提示するに留める。

### Consequences

- 秘密鍵の生成に関与しないため、NFR-1（資格情報の不取扱い）が明確に保たれる
- 失敗時の巻き戻しが不要になる。鍵を作ったが登録に失敗した、という中間状態を持たない
- 初回セットアップに手動ステップが残る。`doctor` の出力にコピー可能なコマンドを含めて緩和する
- 鍵の命名規約を強制しないため、既存環境からの移行が容易になる（副次的利益）

### Alternatives considered

- **`init` で鍵生成まで行う**: 体験は向上するが、責務と失敗モードが増え、秘密鍵に触る設計になる。却下
- **`--with-keygen` フラグで opt-in**: 将来の拡張余地として残すが、初版では実装しない

## ADR-0008: upstream cli/cli#12459 が実装された場合の出口戦略

**Status:** Accepted

### Context

[cli/cli#12459](https://github.com/cli/cli/issues/12459) はまさに本ツールが埋めている穴を埋める提案である（`git config github.account` を読んで自動切替）。実装されれば、本ツールの gh 関連部分は不要になる。

現時点で open・メンテナ応答なしだが、実装される可能性は無視できない。それを理由に着手を止めるべきではないが、実装されたときに負債にならない構造にしておく必要がある。

### Decision

**gh 切替の責務を、マニフェスト・git 生成・ssh 生成から明確に分離する。**

具体的には、`ghmultiaccount.account` というキーを**アカウント別 git 設定ファイルに書き込む**（ADR-0003 で既に決定済み）。#12459 が `github.account` として実装された場合、生成器は同じ値を `github.account` にも書き出すだけでよい。

そのうえで #12459 が実装された時点で `shell_integration = "none"` を既定に切り替え、`.envrc` / ラッパーの生成を deprecated とする。マニフェスト・git 生成・ssh 生成は影響を受けない。

### Consequences

- upstream の変更が本ツールの中核を壊さない。影響範囲がシェル統合層に限定される
- #12459 が実装されても、**マニフェストによる宣言的管理・ssh Host エイリアス生成・`doctor` の価値は残る。**本ツールは「gh の穴埋め」ではなく「複数アカウント環境の宣言的管理」として位置づけられる
- README にこの位置づけを書くことで、利用者が upstream の動向で不安にならない
- 逆に、#12459 が実装されないまま長期間経過する場合も設計を変える必要がない

### Alternatives considered

- **#12459 を待って着手しない**: open・メンテナ応答なしの状態で待つ合理性がない。却下
- **#12459 に PR を出す**: 上流に貢献する価値はあるが、git / ssh 生成とマニフェスト管理の課題は #12459 では解決されない。本ツールと排他ではないため、並行して検討する

## 決定事項の依存関係

```
ADR-0001 (生成器方式)
  ├─ ADR-0002 (物理分離 + include 1行)      ← T1 の検証結果に依存
  ├─ ADR-0003 (.envrc から解決を委譲)       ← T4/T6/T7 の検証結果に依存
  │    └─ ADR-0008 (出口戦略)               ← ghmultiaccount.account キーを共有
  ├─ ADR-0004 (GH_CONFIG_DIR / GH_TOKEN)
  │    └─ ADR-0006 (direnv 非必須)
  ├─ ADR-0005 (Rust)
  └─ ADR-0007 (鍵生成はスコープ外)
```

ADR-0002 と ADR-0003 は実機検証（Requirements 第4節 T1〜T7）に直接依存する。git のバージョン更新でこれらの挙動が変わると決定の前提が崩れるため、NFR-5 の統合テストで固定する。
